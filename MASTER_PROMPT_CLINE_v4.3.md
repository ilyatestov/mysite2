## 0.0.2. БАЗОВЫЙ СТЕК ДЛЯ ПУСТОГО ПРОЕКТА

Если папка действительно пустая и в ней нет существующего стека, используй следующий практичный стек по умолчанию, если установленные версии инструментов позволяют его запустить:

- Backend: Python + FastAPI.
- База данных локального прототипа: SQLite.
- Доступ к БД: SQLAlchemy 2.x.
- Миграции: Alembic.
- Валидация схем и DTO: Pydantic.
- Пароли: Argon2id через проверенную библиотеку.
- Сессии: случайный непрозрачный токен в HttpOnly cookie; на сервере хранить только безопасно обработанный идентификатор/хэш токена и метаданные сессии, предусмотреть отзыв и истечение срока.
- Frontend: HTML5 + CSS3 + Vanilla JavaScript ES modules, если нет веской причины выбирать иной frontend.
- API: REST под префиксом `/api/v1`, OpenAPI/Swagger из реально зарегистрированных маршрутов.
- Тесты: pytest + HTTPX/TestClient; браузерные E2E через Playwright, если браузер/зависимости реально доступны.
- Линтинг: Ruff; покрытие — pytest-cov, если доступно.
- Запуск Windows: `.venv`, `start.bat`, `run_tests.bat` и точные команды в `README.md`.

SQLite — локальное хранилище для прототипа, не финальная рекомендация для высокой production-нагрузки. Модель и миграции делай так, чтобы последующий переход на PostgreSQL был реалистичным. Не используй JSON-файлы или `localStorage` как live-базу пользователей/сообщений/ролей.

Если Python или требуемые зависимости нельзя установить/использовать, проверь уже доступный Node.js LTS и выбери минимальный backend на Express/Fastify с SQLite и аналогичным уровнем безопасности. Не смешивай два backend-стека. Обоснуй выбор и заблокированные пункты в `DECISIONS.md`. Не переключайся на статический сайт только ради простоты, пока есть доступный способ поднять локальный backend.

### Рекомендуемая структура нового проекта

Адаптируй структуру, не создавая бессмысленные папки:

- `app/` — backend-приложение;
- `app/api/v1/` — REST-маршруты;
- `app/core/` — конфигурация, безопасность, сессии, зависимости;
- `app/models/` — модели БД;
- `app/schemas/` — схемы входных/выходных данных;
- `app/services/` — бизнес-логика;
- `app/repositories/` — доступ к данным, если он оправдан;
- `app/static/` или `frontend/` — HTML/CSS/JS;
- `migrations/` — миграции;
- `tests/unit/`, `tests/integration/`, `tests/e2e/` — раздельные уровни тестов;
- `scripts/` — безопасные CLI/backup/seed утилиты;
- `data/` или `instance/` — локальная БД и пользовательские данные, исключённые из Git;
- `docs/` — документация API, администратора, пользователя, развёртывания и миграции.

Создай `.env.example` без настоящих секретов, `.gitignore`, `.clineignore`, `start.bat`, `run_tests.bat`, `README.md` и безопасную CLI-команду создания первого администратора. Не записывай пароль первого администратора в код, seed-файл, историю Git или финальный отчёт.

### 2.1. Постоянное хранение данных

- Для реальных пользователей, паролей, ролей, постов, сообщений и настроек используй серверное хранилище данных.
- Используй существующую БД. Для нового локального проекта допускается SQLite, если она подходит по нагрузке и окружению; при необходимости используй уже настроенную реляционную БД.
- Создай миграции схемы и ограничения целостности: первичные/внешние ключи, уникальность, индексы, обязательные поля.
- Все операции записи выполняй на backend через проверяемые сервисы/API.
- Не используй `localStorage` как основную БД, как источник прав доступа или для хранения паролей, токенов и чувствительных персональных данных.
- `localStorage` можно использовать только для безвредных UI-настроек, например темы или состояния бокового меню.
- JSON-файлы допустимы как начальные seed-данные, настройки разработки или формат импорта/экспорта, но не как иллюзия серверной записи из браузера.
- Предусмотри экспорт данных и резервное копирование, если это соответствует выбранной БД.

### 2.2. Пароли и сессии

- Пароли обрабатывай только на backend.
- Используй современный специализированный алгоритм хэширования паролей: Argon2id предпочтительно; если он недоступен в выбранном стеке — bcrypt или scrypt с корректными параметрами.
- Не используй MD5, SHA-1, обычный SHA-256 или самодельный хэш для хранения паролей. Не переноси парольное хэширование в браузер через Web Crypto API с константной солью: такой подход не заменяет специализированный password hashing и серверную защиту. Web Crypto допустим для иных криптографических задач, но не как замена Argon2id/bcrypt/scrypt для паролей.
- Никогда не храни и не логируй пароль в открытом виде.
- Реализуй вход, выход, проверку текущей сессии и корректное завершение/инвалидацию сессии.
- Для cookie-сессий используй `HttpOnly`, `SameSite` и `Secure` в HTTPS-окружении; корректно настрой режим локальной разработки.
- Защити приложение от фиксации сессии: обновляй идентификатор сессии после входа и изменения привилегий.
- Учитывай истечение срока действия сессии и возможность отзыва сессий.
- Не клади секрет сессии в исходный код. Используй переменные окружения и безопасную конфигурацию.

### 2.3. Роли и права

Минимальные роли:

- `guest` — неавторизованный посетитель;
- `user` — обычный пользователь;
- `moderator` — модерация контента и обращений в рамках явно заданных полномочий;
- `admin` — управление сайтом и пользователями.

Реализуй серверную модель прав доступа (RBAC или эквивалент).

**Критически важно:** проверка роли должна происходить на backend на каждом защищённом маршруте и для каждой операции с объектом. Скрытие кнопки в интерфейсе не является защитой.

Проверь, что:
- обычный пользователь не может открыть админские API прямым запросом;
- пользователь A не может читать, менять или удалять приватные данные пользователя B;
- пользователь не может назначить себе роль `admin` через форму, запрос, импорт или изменение профиля;
- нельзя повысить роль подменой ID, параметра URL, тела запроса или данных браузера;
- модератор не может выполнить действия, доступные только администратору.

Первого администратора создавай безопасной процедурой начальной настройки (CLI-команда, защищённый setup-процесс или переменные окружения с одноразовой активацией). Не зашивай логин и пароль администратора в публичный код и не коммить их в Git. Не оставляй открытой регистрацию администраторов.

### 2.4. Защита веб-приложения

Проверь и реализуй применимые меры:

- XSS: безопасный вывод пользовательского текста, контекстное экранирование; не вставляй непроверенный текст через `innerHTML`.
- SQL injection: параметризованные запросы или безопасный ORM/query builder.
- CSRF: токены или подходящая защита для cookie-аутентификации.
- Перебор паролей: ограничение частоты запросов на регистрацию, вход, восстановление пароля и отправку сообщений.
- IDOR/BOLA: проверка права доступа к каждой записи по её ID.
- Open redirect: проверка адресов перенаправления.
- Path traversal: безопасная работа с путями и файлами.
- Загрузка файлов: проверка MIME-типа и размера, случайные серверные имена, запрет исполнения загруженных файлов, хранение вне исполняемой директории, если возможно.
- Security headers: настрой безопасные заголовки, совместимые с приложением.
- CORS: не разрешай всем доменам доступ без реальной необходимости.
- Ошибки: не отдавай клиенту stack trace, SQL, секреты и внутреннюю конфигурацию.
- Логи: не записывай пароли, session ID, токены и содержимое приватных сообщений без необходимости.
- Зависимости: проверь известные уязвимости доступными локальными инструментами; не обновляй пакеты вслепую.

Валидация входных данных обязательна на backend. Клиентская валидация нужна для удобства, но не заменяет серверную.

### 2.5. Стандарты кода

- Следуй стилю и соглашениям уже используемого проекта.
- Не создавай монолитный файл на тысячи строк, но и не дроби код искусственно.
- Не устанавливай ограничение «не более 80 строк в одном файле». Размер файла должен определяться ответственностью модуля и читаемостью.
- Разделяй маршруты, бизнес-логику, доступ к данным, валидацию и UI настолько, насколько это оправдано стеком.
- Используй единый формат ответов API и единый обработчик ошибок.
- Добавляй комментарии там, где логика неочевидна, а не к каждой строке.
- Не оставляй фиктивные кнопки, пустые обработчики, заглушки под видом готовых функций и тестовые данные в production-конфигурации.

## 2.6. ЕДИНЫЙ ИНТЕРФЕЙС ДАННЫХ И ПОДГОТОВКА К МИГРАЦИИ

Фронтенд не должен быть жёстко привязан к способу хранения данных.

- Создай или сохрани единый слой доступа к данным: например, `assets/js/data.js`, `assets/js/api.js` или существующий аналог.
- Все страницы и UI-компоненты обращаются к данным через этот слой, а не выполняют произвольные операции с хранилищем напрямую.
- Интерфейс слоя должен предоставлять понятные методы чтения/создания/обновления/удаления сущностей и единообразно обрабатывать загрузку, ошибки и пустые ответы.
- В локальном прототипе эти методы должны обращаться к локальному backend через `fetch('/api/...')` или эквивалентный API выбранного стека.
- Позже реализация data/API-слоя может быть переключена на production API без переписывания всей логики интерфейса.
- Не дублируй все серверные данные в `localStorage` «для стабильности»: это создаёт конфликты и ложный источник истины.
- `localStorage` разрешён для некритичных настроек интерфейса и гостевой корзины, если в ней нет персональных/платёжных данных. Для авторизованной корзины и заказов источником истины должен быть backend.
- Кэширование допускается только как явно обозначенный кэш с правилами обновления/инвалидации. Кэш не может быть источником прав доступа, ролей, баланса, статусов заказов или приватных данных.

Пример логического контракта (адаптируй к фактическому проекту, не копируй вслепую):

- `getPosts(params)`, `getPost(idOrSlug)`, `createPost(data)`, `updatePost(id, data)`, `deletePost(id)`;
- `getCurrentUser()`, `register(data)`, `login(credentials)`, `logout()`;
- `getConversations()`, `getMessages(conversationId, params)`, `sendMessage(conversationId, data)`;
- `getProducts(params)`, `createOrder(data)`.

Контракт, фактические endpoint-ы и формат ответов задокументируй в `DECISIONS.md` и `README.md`.

Если фронтенд действительно использует Vanilla JS без сборщика, слой `assets/js/data.js` должен предоставлять единый набор функций, например `getData`, `saveData`, `createData`, `updateData`, `deleteData`, `loadData`, `initData`, `exportData`, `importData`. Адаптируй точные сигнатуры к выбранному API. `initData()` должен безопасно и идемпотентно загружать seed-данные на сервере только при первоначальной инициализации, а не перезаписывать БД при каждой загрузке страницы. Импорт/экспорт должен валидировать схему и быть доступен только уполномоченным ролям.

Для Vanilla JS допустима следующая примерная структура (не создавай дубли, если в проекте уже есть эквиваленты):

- `assets/css/style.css` — базовые стили, переменные, сетка, header/footer, адаптивность;
- `assets/css/components.css` — модальные окна, тосты, таблицы, пагинация, бейджи, алерты, индикаторы загрузки;
- `assets/js/utils.js` — форматирование, генерация ID для сущностей, где ID создаётся клиентом и затем проверяется сервером, debounce/throttle и другие общие функции;
- `assets/js/security.js` — клиентская безопасная обработка/экранирование для UI и удобная валидация. Не хэшируй здесь пароли;
- `assets/js/ui.js` — общие UI-компоненты;
- `assets/js/data.js` или `api.js` — единый слой доступа к backend;
- `assets/js/auth.js`, `blog.js`, `messages.js`, `admin.js`, `shop.js` — только если такое разделение соответствует проекту;
- `assets/js/main.js` — инициализация интерфейса и общего меню.

Возможные страницы при соответствующем функционале: `index.html`, `blog.html`, `post.html`, `shop.html`, `cart.html`, `login.html`, `register.html`, `profile.html`, `messages.html`, `referral.html`, `admin.html`. Если используется SPA/router или серверные шаблоны, не создавай HTML-файлы искусственно — обеспечь те же маршруты в существующей архитектуре.

## 2.7. ЛОКАЛЬНЫЙ HTTP-СЕРВЕР, ЗАПУСК И CORS

**Не открывай приложение через `file://`, если страницы используют `fetch()`, модули, API или загрузку JSON.** Запускай его по локальному адресу, например `http://127.0.0.1:8000`.

1. На этапе аудита выясни, нужен ли проекту только статический сервер или полноценный backend.
2. Если проект остаётся полностью статическим и нужен лишь предпросмотр файлов, можно использовать Python: `python -m http.server 8000 --bind 127.0.0.1`. При необходимости создай удобный `server.py` или `start.bat`, который запускает команду из корня проекта.
3. Если реализован backend, запускай именно его штатной командой. Не подменяй полноценный API статическим `http.server`: он не обеспечивает авторизацию, БД, серверные проверки ролей и бизнес-логику.
4. Для backend-проекта создай удобный сценарий запуска для Windows (`start.bat` и/или `server.py`, если выбран Python-стек) и укажи точные команды в `README.md`.
5. По возможности используй один origin для фронтенда и API. Тогда CORS обычно не требуется. Если разные origin неизбежны, настрой CORS только для конкретных локальных адресов разработки; не используй `*` вместе с credentials/cookies.
6. Не пытайся «лечить CORS» отключением браузерной защиты. Не запускай браузер в небезопасном режиме.
7. Привязывай локальный сервер к `127.0.0.1`, если доступ из локальной сети не требуется. Не открывай порт наружу без необходимости.
8. Если порт занят, определи причину и выбери свободный локальный порт. Обнови документацию и ссылки согласованно.
9. README должен содержать проверенную команду старта, URL, команду остановки и команды запуска тестов.

**Важно:** `python -m http.server` решает только задачу раздачи статических файлов по HTTP. Он не превращает JSON-файлы в безопасную многопользовательскую БД и не реализует backend API.

## 2.8. ПОЛНОЦЕННЫЙ API И КОНТРАКТЫ

API — обязательная часть сайта, а не побочная функция. Если проект создаётся с нуля, реализуй API с версионированием `/api/v1` и единым форматом ответов.

Минимальные группы маршрутов (точные endpoint-ы согласуй с реальной архитектурой и задокументируй):

- `auth`: регистрация, вход, выход, текущая сессия, смена пароля; восстановление пароля только с честно обозначенным локальным dev-режимом.
- `users`: собственный профиль, безопасное редактирование, список/карточка пользователей только для разрешённых ролей, блокировка и изменение ролей только администратором.
- `posts`, `categories`, `tags`: публичное чтение опубликованного контента, административный CRUD, черновики/публикация/архивация.
- `comments`: создание и управление собственными комментариями, модерация для модератора/администратора.
- `conversations`, `messages`: диалоги, участники, отправка, чтение, отметка прочитанного, непрочитанные.
- `referrals`: личный код, приглашённые регистрации, статистика и защита от повторного/самореферального начисления.
- `products`, `cart`, `orders`: публичный каталог, серверная корзина для авторизованных пользователей, расчёт цен на сервере, тестовый заказ без оплаты.
- `notifications`: список, счётчик и отметка прочитанного.
- `settings`: публичные безопасные настройки и административное изменение закрытых настроек.
- `admin/dashboard`, `admin/audit-logs`: агрегированная статистика и журнал действий с ролью admin.
- `health`: локальная проверка работоспособности приложения и подключения к БД без раскрытия секретов.

Для API установи и документируй:

- единый формат успеха и ошибки (например, `data`, `error`, `message`, `request_id`);
- правильные HTTP status codes;
- пагинацию и сортировку с верхними пределами размера страницы;
- серверную валидацию типов, длины, диапазонов и разрешённых полей;
- защиту от массового присваивания полей (`role`, `owner_id`, `author_id`, `price`, `status` не должны слепо приниматься от клиента);
- idempotency/защиту от повторной отправки там, где это необходимо;
- журналирование только безопасных метаданных;
- интерактивную локальную OpenAPI-документацию и файл `docs/API_REFERENCE.md` с фактическими маршрутами, методами, параметрами, ролями, телами запросов, ответами и ошибками.

Создай отдельные API-тесты на позитивные и негативные сценарии. Документация должна соответствовать фактическому OpenAPI и реальному коду, а не быть фантазией.

## 2.9. РЕФЕРАЛЬНАЯ СИСТЕМА — ПОЛНАЯ ЛОГИКА

Реферальная система должна работать через backend и БД:

1. Каждому пользователю сервер назначает уникальный случайный реферальный код.
2. Публичная ссылка формируется по адресу сайта с `?ref=CODE`.
3. При открытии ссылки сайт корректно сохраняет атрибуцию до регистрации (например, в ограниченной по времени серверной сессии/подписанном cookie или через валидируемый код в форме регистрации). Не доверяй произвольному `referrer_id` от клиента.
4. При регистрации сервер самостоятельно ищет действующий код и сохраняет связь «пригласивший — приглашённый».
5. Запрещены самореферал, повторная привязка к другому пригласившему, циклы и дубли.
6. Реферальная связь должна иметь уникальные ограничения БД и транзакционную запись.
7. В профиле отображаются личная ссылка, количество приглашённых, список/даты и статусы, если они существуют.
8. Администратор видит агрегированную статистику и может проверять подозрительные записи, но не может произвольно переписывать историю без audit log.
9. Не выдумывай денежные выплаты, коэффициенты и бонусы. Пока бизнес-условия не заданы, реализуй учёт приглашений и статистику без денежного вознаграждения.
10. Покрой тестами валидный код, неверный код, истечение атрибуции, самореферал, повторную регистрацию, гонку двух регистраций, попытку подмены referrer ID и отсутствие дублирующих начислений.

Реализуй модули на основании результатов аудита. Сохраняй уже работающие функции. При ограниченном времени сначала заверши P0, затем P1 и только после этого переходи к P2.

## 3. МОДУЛЬ P0 — ОСНОВА САЙТА И НАВИГАЦИЯ

Проверь или реализуй:

- Страницы входа, регистрации, профиля, блога, отдельной публикации, сообщений, админки, магазина и корзины (если магазин входит в scope).
- Страницы 404 и безопасной обработки ошибок.
- Состояния загрузки, пустых списков, ошибок, успешных операций и отсутствия доступа.
- Корректную работу ссылок, кнопок, форм, модальных окон, таблиц и пагинации.

Не считай страницу готовой только потому, что она открывается: проверь все доступные элементы управления.

## 4. МОДУЛЬ P0 — РЕГИСТРАЦИЯ И АВТОРИЗАЦИЯ

Реализуй или проверь:

1. Регистрацию с username, email, password и подтверждением пароля.
2. Нормализацию и уникальность username/email с учётом регистра там, где это требуется.
3. Серверную валидацию длины и формата полей.
4. Политику пароля: разумная минимальная длина, защита от тривиальных паролей и отсутствие искусственно чрезмерных требований.
5. Вход по email/username согласно выбранной логике.
6. Выход и прекращение сессии.
7. Проверку текущего пользователя.
8. Корректные сообщения об ошибках без раскрытия, существует ли конкретный email, когда это создаёт риск перечисления аккаунтов.
9. Ограничение частоты попыток входа.
10. Восстановление пароля — только если механизм доставки реально настроен. В локальной разработке используй безопасный dev-механизм, не отправляй письма фиктивно и не показывай секретный токен обычным пользователям.
11. Подтверждение email — если это поддерживается конфигурацией почты; иначе честно обозначь статус функции.
12. Защиту от CSRF и фиксации сессии.

После регистрации обычный пользователь получает только обычную роль. Никакие поля формы не должны позволять выбрать себе административную роль.

## 5. МОДУЛЬ P0 — ПРОФИЛИ И УПРАВЛЕНИЕ ПОЛЬЗОВАТЕЛЯМИ

Профиль пользователя:

- история собственных действий/активности, если она реально поддерживается.

Администрирование пользователей:

- список пользователей с поиском, фильтрами, сортировкой и пагинацией;
- просмотр карточки пользователя;
- редактирование только разрешённых полей;
- изменение роли только администратором и с проверкой полномочий;
- блокировка/разблокировка или приостановка аккаунта;
- удаление с подтверждением и понятной политикой связанных данных;
- защита от удаления последнего действующего администратора;

Все административные изменения должны попадать в отдельный журнал действий (`audit_logs` или `admin_audit_logs`): кто выполнил действие, когда, над каким типом/ID объекта и с каким результатом. Не записывай пароли, токены, session ID и полный текст приватных сообщений. Записи журнала не должны редактироваться обычными пользователями.

Удаление пользователя не должно случайно разрушать связанные публикации, сообщения и историю. Выбери обоснованную политику: soft delete, анонимизация или каскадное удаление — и опиши её в документации.

# ЧАСТЬ V. ТЕСТИРОВАНИЕ И ПРОВЕРКИ

## 16. ГЛАВНОЕ ПРАВИЛО ТЕСТИРОВАНИЯ

**Не отмечай тест как PASS, если ты его фактически не запускал и не получил подтверждённый результат.**

Каждая проверка получает один из статусов:

- `PASS` — реально выполнена и пройдена;
- `FAIL` — выполнена и обнаружена ошибка;
- `BLOCKED` — невозможно выполнить из-за отсутствующей среды/инструмента/доступа;
- `NOT RUN` — не запускалась.

Для каждого `BLOCKED` и `NOT RUN` укажи конкретную причину. Не заменяй проверку рассуждением по исходному коду.

## 17. УРОВНИ ТЕСТИРОВАНИЯ

### 17.1. Сборка, запуск и статический анализ

Создай или используй автоматизированный test runner. Если стек допускает Node.js, можно добавить `tests.js` или набор тестов на встроенном `node:test`; для Python — `pytest`/`unittest`; для другого стека — его штатный инструмент. Не создавай тестовый файл ради галочки: он должен запускать реальные проверки.

Минимально проверь наличие ключевых файлов/маршрутов, валидность JSON seed-файлов, конфигурацию и синтаксис исходников. Если используется JSON, проверь каждый файл парсером, а не регулярным выражением.

- установка зависимостей по lock-файлу;
- проверка синтаксиса и компиляции;
- lint/format/typecheck, если инструменты предусмотрены проектом;
- production build, если он существует;
- проверка конфигурации и обязательных переменных окружения;
- отсутствие случайно включённых секретов;
- проверка известных уязвимостей зависимостей доступными инструментами.

### 17.2. Модульные тесты

Проверь отдельно:

- валидацию входных данных;
- обработку ошибок;
- функции авторизации и проверки ролей;
- бизнес-логику публикаций;
- работу пагинации, поиска и фильтров;
- подсчёт просмотров;
- реферальную логику;

- обработку дат и временных зон;

### 17.3. Интеграционные тесты

Проверь взаимодействие API, БД и middleware:

- чтение и изменение профиля;
- создание/редактирование/публикация/удаление поста;
- категории, теги, поиск и пагинация;
- создание, чтение и отправка сообщений;
- права доступа к диалогам;
- комментарии и модерация;
- административные действия;
- сохранение и чтение настроек;
- миграции и ограничения БД;
- обработка некорректных данных и отсутствующих записей.

### 17.4. End-to-end тесты в браузере

Используй уже установленный инструмент браузерного тестирования. Если его нет, проверь возможность безопасно добавить подходящий локальный инструмент (например, Playwright), учитывая доступные runtime и ресурсы.

Не проверяй полноценное приложение через `file://`. Запускай локальный HTTP-сервер тем способом, который предусмотрен стеком.

Проверяй реальные действия пользователя:

1. Гость открывает главную страницу и блог.
2. Гость пытается открыть профиль, сообщения и админку — получает ожидаемое ограничение/редирект.
3. Новый пользователь регистрируется.
4. Новый пользователь входит и выходит.
5. Пользователь меняет разрешённые данные профиля.
6. Пользователь открывает опубликованный пост и ищет публикации.
7. Пользователь создаёт комментарий, если комментарии включены.
8. Пользователь отправляет личное сообщение/обращение.
9. Пользователь видит только свои диалоги и уведомления.
10. Администратор входит и открывает дашборд.
11. Администратор создаёт, редактирует, публикует и удаляет тестовый пост.
12. Администратор ищет пользователя, меняет допустимые поля и меняет статус тестового аккаунта.
13. Администратор отвечает на обращение, если модуль поддержки реализован.
14. Администратор изменяет настройки сайта.
15. После обновления страницы и повторного входа данные сохраняются корректно.
16. Если магазин реализован: пользователь просматривает каталог, добавляет товар в корзину, меняет количество, оформляет тестовый заказ; сумма заказа проверяется сервером и после перезапуска сервера данные остаются согласованными.
17. Если магазин реализован: администратор создаёт, редактирует и архивирует тестовый товар; обычный пользователь не может менять товары или чужие заказы.
18. Некорректные формы показывают сообщения об ошибках и не портят данные.
19. На мобильной ширине меню и основные сценарии остаются рабочими.

### 17.5. Матрица ролей и безопасности

Создай тестовые учётные записи для ролей `guest`, `user A`, `user B`, `moderator`, `admin` там, где роль реализована. Проверь матрицу доступа для каждого защищённого действия.

Обязательные отрицательные тесты:

- гость вызывает защищённый API напрямую;
- обычный пользователь вызывает admin API напрямую;
- user A пытается получить диалог user B;
- user A пытается изменить профиль user B;
- user A пытается удалить чужую публикацию/комментарий;
- обычный пользователь подменяет роль в запросе;
- пользователь пытается получить доступ к неопубликованному посту;

- попытки доступа к несуществующим объектам;
- попытки выполнить действие после выхода из системы.

Проверяй безопасность только на локальной тестовой среде и на тестовых данных. Не проводи разрушительные нагрузочные или атакующие проверки на внешних системах.

### 17.6. UI, адаптивность и доступность

Проверь минимум следующие размеры окна:

- 390×844;
- 768×1024;
- 1024×768;
- 1366×768;

Проверь:

- доступность всех действий с клавиатуры, где применимо;

- подписи полей и понятные ошибки;
- читаемость текста и контраст;
- состояния загрузки и пустых списков.

### 17.7. База данных и сохранность данных

- Убедись, что перезапуск сервера не удаляет данные.
- Проверь, что операции, требующие атомарности, выполняются транзакционно.
- Проверь поведение внешних ключей при архивировании/удалении.
- Проверь резервное копирование и восстановление на отдельной тестовой копии.
- Убедись, что тесты не используют пользовательскую базу.
- Проверь отсутствие дублей при повторной отправке формы и повторном запросе.

### 17.8. Производительность и стабильность

В рамках доступной среды проверь:

- отсутствие очевидных N+1-запросов на основных списках;
- пагинацию больших списков;
- индексы часто используемых полей;
- отсутствие бесконечных циклов и повторных сетевых запросов;
- корректную обработку таймаутов и ошибок БД;
- отсутствие критических ошибок в консоли и серверных логах;
- разумное время загрузки основных страниц на локальном окружении.

Не называй тест нагрузочным, если не создавал контролируемую нагрузку и не измерял результат.

## 17.9. РАСШИРЕННЫЙ НАБОР ТЕСТОВ И КРИТЕРИИ ПОКРЫТИЯ

Создай не только несколько демонстрационных тестов, а систематический набор тестов для каждого реально реализованного модуля.

Минимальные требования:

- Все P0-функции должны иметь unit- и integration-тесты для основных позитивных и негативных веток.
- Для каждого защищённого API endpoint должны существовать проверки гостя, обычного пользователя и разрешённой роли (по применимости).
- Для приватных сущностей обязательно проверяй сценарии «свой объект / чужой объект / несуществующий объект».
- Все критические правила бизнес-логики (регистрация, роль, доступ к сообщению, реферальная привязка, расчёт заказа, публикация) должны иметь отдельные тесты.
- Стремись к покрытию не менее 80% для критической backend-бизнес-логики, если инструмент покрытия доступен. Не гонись за процентом за счёт бессмысленных тестов и никогда не заявляй процент без реального отчёта.
- Используй фикстуры и фабрики тестовых данных. Каждый тест должен быть изолированным и повторяемым.
- Перед каждым тестовым запуском убедись, что тесты подключены к отдельной временной БД. Запрещено очищать пользовательскую/основную базу.
- Проверь повторный запуск тестов: результат должен быть стабилен и не зависеть от порядка тестов.

Добавь следующие специальные проверки, если они применимы к выбранной реализации:

1. Параллельные регистрации с одинаковым email/username — должен сохраниться только один уникальный пользователь.
2. Повторный/одновременный реферальный запрос — не должно быть дублей связей/бонусов.
3. Попытки mass assignment: подмена `role`, `user_id`, `author_id`, `owner_id`, `is_admin`, `price`, `order_total`.
4. CSRF для cookie-аутентификации и проверка `SameSite`/`HttpOnly` флагов.
5. Отозванная/истёкшая сессия и повторное использование старого токена.
6. Rate limit логина/регистрации/сообщений с проверкой корректного ответа сервера.
7. XSS payload в username, biography, post, comment, message, product и настройках — пользовательский текст не должен исполняться.
8. Попытки получить приватный диалог/уведомление/заказ другого пользователя через замену идентификатора.
9. Попытка пользователя изменить или удалить последний аккаунт администратора.
10. Манипуляции ценой и количеством товара на клиенте — итог заказа должен быть вычислен на сервере.
11. Повторное нажатие/повторный запрос оформления заказа — не создаёт дубликаты.
12. Ошибка БД посреди транзакции — не оставляет частично сохранённое состояние.
13. Невалидный upload (если загрузки реализованы): неверное расширение/MIME/размер/имя файла и path traversal.
14. Пагинация: отрицательные, нулевые, чрезмерные значения и пустой набор результатов.
15. Миграции: создание чистой БД, обновление до текущей версии и проверка схемы.
16. Backup/restore: восстановление на отдельную тестовую БД и проверка количества/связей тестовых записей.
17. Негативные проверки CORS и security headers для локального окружения.
18. Отсутствующие обязательные env-переменные и некорректная конфигурация — приложение должно завершаться с понятной безопасной ошибкой.

Результаты тестирования должны быть воспроизводимыми: в отчёте указывай команды, версии, количество тестов и итоговые статусы. Исправляя тест, не ослабляй его условие только ради зелёного статуса: сначала убедись, что требование теста корректно.

# ЧАСТЬ VI. ИСПРАВЛЕНИЕ ДЕФЕКТОВ И РАБОЧИЙ ПРОЦЕСС

## 18. ЦИКЛ РАБОТЫ ДЛЯ КАЖДОЙ ФУНКЦИИ

Для каждого модуля используй одинаковый цикл:

1. Изучи соответствующий существующий код.
2. Сформулируй ожидаемое поведение и критерии готовности.
3. Определи затрагиваемые файлы и данные.
4. Сделай резервную копию или используй Git/ветку для возможности отката.
5. Реализуй минимально полное решение.
6. Проведи статические проверки и профильные тесты.
7. Исправь обнаруженные ошибки.
8. Повтори тесты после исправлений.
9. Проверь связанные модули на регрессии.
10. Зафиксируй фактический результат в `NIGHT_LOG.md` и `TEST_REPORT.md`.
11. Только после этого отмечай модуль завершённым.

Не меняй много несвязанных модулей одновременно, если это затрудняет поиск регрессий.

## 19. ОБРАБОТКА ОШИБОК

- При ошибке сначала зафиксируй точную команду, сообщение и контекст.
- Для временной ошибки повтори операцию не более двух раз.
- При ошибке JSON/парсинга проверь исходный файл, кодировку, кавычки и формат; не пропускай файл автоматически, если он критически важен для приложения.
- При ошибке записи проверь права, путь, свободное место и наличие блокировки файла. Не перезаписывай целый файл случайным содержимым.
- При ошибке Git проверь `git status`, конфликт и корректность репозитория. Не используй разрушительные команды для обхода проблемы.
- Если задача заблокирована, запиши её в лог и переходи к независимой задаче.
- Если обнаружена критическая уязвимость или риск повреждения данных, не продолжай действия, которые могут усугубить проблему. Сначала локализуй риск, сохрани данные и зафиксируй блокер.
- Не скрывай пропуски и не подменяй FAIL статусом PASS.
- Не исправляй упавший тест простым комментированием проблемного кода или подстановкой Mock в основную реализацию. Mock допустим только внутри изолированного теста для независимой внешней зависимости и должен быть явно обозначен. Если исправить дефект не удалось, оставь FAIL/BLOCKED, опиши влияние и продолжай независимые проверки.
